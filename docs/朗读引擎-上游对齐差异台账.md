# 朗读引擎与上游「阅读」(legado) 的差异台账

> 用途：本仓库的朗读引擎以**上游阅读**为基底（SK 是上游的超集），只有少数几处是**有意保留的差异**。日后同步上游、或审查「是不是抄错了」时，先看这份台账，不要把这些差异当成缺陷改回去。
> 范围：只覆盖朗读引擎（听书/朗读服务、TTS、缓存、按键映射）。UI 用 SK 自己的，不在对齐范围内。

## 2. 有意保留的差异（改回去即回归）

| # | 差异 | 上游做法 | SK 做法 | 原因 | 回归锁 |
|---|---|---|---|---|---|
| 1 | 音量键翻页闸门 | 删掉 `volumeKeyPage` / `volumeKeyPageOnPlay`，音量键完全交给映射 | 保留两个开关：`volumeKeyTakeoverActive()` 决定是否接管（`volumeKeyPage`，朗读中还要 `volumeKeyPageOnPlay`，插画音频播放时放行） | SK 用户习惯「关掉音量键翻页、用音量键调音量」，上游删掉即失去该能力 | `BluetoothKeyMappingGuardTest.reader routes media and volume keys through one entry each` |
| 2 | 音量键朗读态默认动作 | `ACTION_NONE`（靠映射表空转） | `ACTION_PREVIOUS_PAGE` / `ACTION_NEXT_PAGE` | 闸门已经决定「朗读中是否接管」，再给 NONE 会让开了闸门的用户按音量键毫无反应 | `BluetoothKeyMappingGuardTest.volume keys default to page turning in both slots`（已变异证伪） |
| 3 | 播放暂停键未朗读时的行为 | `ui.toggleReadAloud()` 直调 Activity 回调 | `MediaButtonReceiver.readAloud(context)` | `readAloudByMediaButton` / `mediaButtonOnExit` / `MEDIA_BUTTON` 三项策略都在该入口里，直调回调会绕过它们 | `BluetoothKeyMappingGuardTest.toggle falls back to the shared read aloud entry` |
| 4 | 预测字幕的注入点与生效条件 | 先把 `mapping` 换成估计值，再 `bindMappingToLayout`；失败就当没绑定 | 只在 `bindMappingToLayout(estimated)` 返回非 null 后才同时替换 `mapping` 与 `layoutBinding` | 本服务 `sessionChapterCanStartWithoutText = true`，正文晚于 `STATE_READY` 就绪是常态；上游写法一旦返回 null，`mapping` 已是估计值却永不重试，整章预测静默失效 | `SourceAudioChapterTimerGuardTest.estimated timing is bound only from state ready` |
| 5 | 预测位置的发布门槛 | 只判页码：`if (!paragraphUnchanged \|\| syncView \|\| predictedPage != pageIndex)` | 抽出 `shouldPublishTextPosition(...)`，**页码与 TTS 位置事件共用**同一门槛 | 否则每个轮询周期都 `postReadAloudTextPosition`，白白驱动阅读页跟随判定与高亮重算 | `PredictedTextPositionTest`、`SourceAudioChapterTimerGuardTest.sync text position publishes through the shared gate` |
| 6 | 备份键表 | 只备份 `bluetoothReadAloudSkipInterval` | 追加 14 个映射键 | 换机恢复后按键映射不该悄悄回默认 | 无（`BackupConfig.readPrefKeys` 为声明式） |

## 3. 已按上游删除的 SK 旧能力（不要复活）

- `PreferKey.mediaButtonPerNext`（耳机上一首/下一首 = 上一章/下一章）：上游用蓝牙映射取代，SK 作者决定直接删除、不做迁移。常量、4 处读点、朗读设置 Basic 组白名单、`pref_config_aloud.xml` 那一行及两条文案均已移除；存量设备上该 pref 值留在 `config.xml` 里但**已无任何读取点**。
- 由此产生的三项用户可见变化（发布说明须写明）：
  1. 阅读页在前台时蓝牙播放/暂停键不再有反应（`KEYCODE_MEDIA_PLAY_PAUSE` 走映射，默认 NONE）；
  2. 阅读页与通知栏的「播放暂停」使用同一 keycode 分支，行为一致；
  3. 未在朗读时，耳机上一首/下一首按「切章」处理（与上游一致），不再有"切段"选项。

## 4. SK 独有、上游没有的引擎能力（同步上游时不得被覆盖）

以下都不在上游代码里，同步上游相关文件时必须逐项确认没被冲掉：

- 实时朗读缓存：`app/src/main/java/io/legado/app/help/tts/TtsCacheManager.kt`、`TtsCacheService`、`TtsCacheJanitor.kt`、`TtsCacheSweep.kt`；`AppConfig.ttsCacheFastRetry` + `FAST_RETRY_SEGMENT_TIMEOUT_SECONDS` + 干涸看门狗（`ReadAloudRealtimeDryWatchdogTest`）。
- 朗读音量增强：`AppConfig.ttsVolumeGain` / `io.legado.app.help.exoplayer.VolumeGain`。
- 听书按章节定时的额度守卫：`decideChapterConsumption(...)`、`audioChapterAdvanced(...)`、`onChapterConsumed()`，以及 `SourceAudioReadAloudService` 的 `chapterPlaybackStart` / `maxPlayedPosition` 记录行（`SourceAudioChapterTimerGuardTest`）。
- 在线朗读「暂停必须真的停声」：`HttpReadAloudService.pauseReadAloud()` / `resumeReadAloud()` 必须 `lifecycleScope.launch { }` 且禁止 `runCatching` 包裹；`prepareScriptMediaItemsWithRetry()`（`ReadAloudPauseOnMainThreadGuardTest`）。
- 朗读面板定位就绪才显示：`ReadAloudPanelPositionGuardTest`。
- 已知**有意保留**的上游偏差（历史决定，非本次范围）：`SourceAudioReadAloudService.setPlaybackSpeed` 静默 `coerceIn(0.5f, 3.0f)`，上游是 toast + return。

## 5. 下次再同步上游朗读引擎时怎么做

1. `git log --oneline 0387359a..upstream/own -- <引擎路径>` 取候选提交，逐个判断是「上游能力」还是「SK 已有」。
2. 上游新能力先在 `test-records/` 写方案 + 派独立审查（默认并行 3 个：结论核查 / 移植细节 / 红线冲突），不要直接改源码。
3. 落地后按 §2 逐条核对差异项，并按 §4 逐条确认 SK 独有能力未被覆盖。
4. 每个独立修改一个提交，保证能单独 `compileAppReleaseKotlin` 通过（`pref` 行与引用它的 Kotlin 白名单必须同提交）。
